## 3. Ответы на контрольные вопросы

**1. Как использование git add -p помогает при отладке через git bisect?**

`git add -p` формирует мелкие атомарные коммиты, каждый из которых меняет только один аспект. При `git bisect` поиск плохого коммита не приведёт к ситуации, когда в одном коммите смешаны фича и баг — можно точно указать, какое изменение вызвало проблему.

**2. Почему наличие requirements.lock.txt критично для командной работы и чем оно лучше обычного requirements.txt с версиями без минорных номеров?**

`requirements.lock.txt` фиксирует точные версии всех пакетов и их зависимостей. Это гарантирует, что все разработчики и CI-среда получат идентичное окружение. `requirements.txt` с версиями типа `flask>=2.0` может привести к разным минорным обновлениям, что иногда ломает совместимость.

**3. В чем преимущество Makefile перед текстовой инструкцией в README?**

Makefile — это исполняемая документация. Вместо того чтобы читать инструкцию и вручную копировать команды, разработчик просто выполняет `make install`, `make test`, `make run`. Это исключает ошибки ручного ввода и всегда синхронизировано с реальным процессом.

**4. Как тесты реализуют принцип «живой документации» и почему фиксация seed важна для воспроизводимости?**
Тесты описывают ожидаемое поведение системы в формате Given-When-Then, который легко читается. Это документация, которая проверяется автоматически и не устаревает. Фиксация `random.seed(42)` делает тесты детерминированными: при каждом запуске генерируются одни и те же «случайные» данные, исключая ложные падения из-за рандомизации.

**5. Что произойдет, если удалить папку venv и выполнить make install на чистой машине? Продемонстрируйте это на практике.**
Make-цель `install` создаст новое виртуальное окружение и установит в него все зависимости из `requirements.lock.txt`. Приложение окажется в том же состоянии, в котором оно было зафиксировано разработчиком. Это продемонстрировано на скриншоте «чистого старта».
